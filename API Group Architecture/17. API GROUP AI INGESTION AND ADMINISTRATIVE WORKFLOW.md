# API GROUP AI INGESTION AND ADMINISTRATIVE WORKFLOW

## PURPOSE

This document defines how API Group information should move from discovery and data entry into the database and ultimately onto the public website.

The system must be designed so that an administrator without coding experience can maintain the collection.

AI should be able to assist with:

- Discovering information
- Creating records
- Updating records
- Identifying duplicates
- Creating relationships
- Adding sources
- Adding descriptions
- Suggesting classifications
- Organizing hierarchy
- Preparing records for review

The database remains the source of truth.

AI is an assistant.

The administrator remains the authority for publication and consequential changes.

---

# 1. CORE WORKFLOW

The intended workflow is:

INFORMATION
↓
AI / ADMINISTRATOR
↓
IDENTIFY RECORD TYPE
↓
SEARCH EXISTING DATABASE
↓
CHECK FOR DUPLICATES
↓
CREATE OR UPDATE RECORD
↓
ADD RELATIONSHIPS
↓
ADD SOURCES
↓
ADD MEDIA
↓
VALIDATE
↓
ADMINISTRATOR REVIEW
↓
PUBLISH
↓
WEBSITE AUTOMATICALLY UPDATES

---

# 2. DATABASE FIRST

AI should work with structured database records.

AI should not primarily generate webpages.

AI should create or update:

- Agencies
- Personnel
- Jurisdictions
- Civic organizations
- Categories
- Dependencies
- Articles
- Sources
- Media
- Tags
- Relationships

The frontend should then render those records.

---

# 3. NO HARDCODED CONTENT

When AI adds a new county, agency, person, or category, it must not modify a static list in a template.

Instead:

AI creates database record.

The database becomes aware of the new record.

The appropriate page queries the database.

The new record appears automatically.

---

# 4. RECORD IDENTIFICATION

Before creating anything, AI should determine:

- What kind of record is this?
- What is the canonical name?
- Does the record already exist?
- What jurisdiction does it belong to?
- What parent organization exists?
- What relationships are known?
- What sources support the information?

---

# 5. DUPLICATE CHECK

AI must search existing records before creating a new entity.

Possible duplicate indicators include:

- Same name
- Alternate spelling
- Abbreviation
- Previous name
- Same website
- Same address
- Same jurisdiction
- Same organization identifier

If a possible duplicate is found, AI should not blindly create another record.

---

# 6. CANONICAL RECORDS

Each real-world entity should have one canonical record whenever practical.

Example:

ONE PERSON

rather than:

PERSON ON AGENCY PAGE A
PERSON ON AGENCY PAGE B
PERSON ON ARTICLE PAGE

All of those displays should reference the same personnel record.

---

# 7. RELATIONSHIPS

AI should create relationships separately from the records themselves.

Example:

PERSON
↓
works for
↓
AGENCY

PERSON
↓
associated with
↓
CIVIC ORGANIZATION

AGENCY
↓
located in
↓
JURISDICTION

ARTICLE
↓
references
↓
AGENCY

---

# 8. RELATIONSHIP TYPES

Relationships should use explicit types whenever possible.

Examples:

- Works for
- Leads
- Located in
- Parent of
- Child of
- Operates in
- Oversees
- Related to
- References
- Published by
- Member of
- Formerly associated with

The relationship vocabulary should be extensible.

---

# 9. SOURCE-FIRST PRINCIPLE

Important factual information should have a source whenever appropriate.

AI should preserve source information rather than merely using a source temporarily and discarding it.

A source may include:

- Name
- URL
- Publication
- Document
- Date
- Description
- Source type

---

# 10. SOURCE ASSOCIATION

Sources should be connected to the records they support.

Examples:

SOURCE
→ supports
→ AGENCY

SOURCE
→ supports
→ PERSON

SOURCE
→ supports
→ ARTICLE

SOURCE
→ supports
→ JURISDICTION

---

# 11. AI-DERIVED INFORMATION

When AI produces information that has not yet been verified, it should be distinguishable from verified information.

Possible statuses:

- Unverified
- Needs review
- Verified
- Published
- Archived

The exact workflow may evolve.

---

# 12. HUMAN REVIEW

AI should not automatically publish potentially consequential information without an appropriate review process.

The administrator should be able to inspect:

- Proposed record
- Proposed changes
- Sources
- Relationships
- Media
- AI notes
- Confidence indicators where appropriate

---

# 13. CHANGE PREVIEW

Before significant changes are committed, the system should provide a readable summary.

Example:

CREATE AGENCY

Name:
Sample Illinois Agency

Type:
State

Jurisdiction:
Illinois

Relationships:
3

Sources:
2

Media:
1

The administrator can then approve or reject the proposed change.

---

# 14. UPDATE PREVIEW

For existing records, show:

BEFORE

and:

AFTER

where practical.

Example:

Agency description changed.

Personnel relationship added.

Website updated.

This makes AI-assisted editing auditable.

---

# 15. ADMINISTRATOR APPROVAL

The administrator should be able to:

- Approve
- Reject
- Edit
- Request changes
- Save draft
- Publish
- Archive

AI should not make irreversible changes silently.

---

# 16. SIMPLE ADMINISTRATIVE INTERFACE

The administrator interface should not assume technical expertise.

Use understandable labels.

Prefer:

Add Agency

over:

Create Agency Entity

Prefer:

Add Person

over:

Insert Personnel Node

Prefer:

Add Relationship

over:

Create Relationship Object

---

# 17. AI DATA ENTRY

An administrator should eventually be able to tell AI something like:

"Add this county to the database."

AI should determine the appropriate structured fields.

The administrator should not need to understand database syntax.

---

# 18. EXAMPLE COUNTY WORKFLOW

INPUT:

"Add Sample County to Illinois."

AI:

1. Searches for existing county.
2. Finds no matching record.
3. Creates county record.
4. Assigns Illinois as parent jurisdiction.
5. Adds description.
6. Adds image if supplied.
7. Adds sources.
8. Presents the record for review.

After approval:

The county becomes available in the county directory.

---

# 19. EXAMPLE AGENCY WORKFLOW

INPUT:

"Add this state agency."

AI:

1. Searches for duplicate.
2. Identifies agency type.
3. Identifies jurisdiction.
4. Creates or updates agency.
5. Adds description.
6. Adds website.
7. Adds image/logo.
8. Creates relationships.
9. Adds sources.
10. Presents proposed changes.

---

# 20. EXAMPLE PERSON WORKFLOW

INPUT:

"Add this person and associate them with this agency."

AI:

1. Searches personnel database.
2. Determines whether person already exists.
3. Creates or updates canonical person record.
4. Creates person-agency relationship.
5. Adds role/position.
6. Adds source.
7. Presents changes for review.

---

# 21. EXAMPLE CATEGORY WORKFLOW

INPUT:

"Create a new API Group category called Public Records."

AI should create:

Category:
Public Records

Description:
Appropriate description

Image:
Optional

Parent:
Appropriate API Group parent

The new category should automatically become available to the website.

---

# 22. EXAMPLE DEPENDENCY WORKFLOW

INPUT:

"Add Government Transparency under Public Records."

AI creates:

Public Records
→ Government Transparency

with:

- Name
- Description
- Parent
- Image
- Status

The sidebar and hierarchy should recognize the new dependency automatically.

---

# 23. EXAMPLE ARTICLE WORKFLOW

INPUT:

"Create a sample article about understanding Illinois county government."

AI should prepare:

- Title
- Summary
- Body
- Image
- Category
- Dependency
- Tags
- Sources

The article remains a database record.

---

# 24. ARTICLE RELATIONSHIPS

AI should be able to identify relevant existing records.

For example:

Article
→ Illinois

Article
→ County

Article
→ Agency

Article
→ Personnel

Article
→ Civic Organization

These relationships should be structured.

---

# 25. AI SHOULD REUSE EXISTING DATA

If API Group already contains an agency profile, AI should reference that agency rather than create another agency record inside an article.

If API Group already contains a personnel profile, AI should reference that profile.

---

# 26. NO DUPLICATE CONTENT SYSTEMS

Do not create:

Article Agency Name

when:

Agency Record

already exists.

The article can display the agency name by referencing the agency record.

---

# 27. AI AND HIERARCHY

AI should understand that hierarchy and records are different.

Example:

Agency Profiles
→ State
→ Illinois
→ State Agencies

is navigation.

A specific agency is a record.

AI should create the appropriate record and relationship rather than creating a new static page.

---

# 28. AI AND SIDEBARS

AI should not manually edit sidebar HTML.

When a new database-driven record is created, the sidebar should discover it automatically.

---

# 29. AI AND CARDS

AI should not manually create individual cards.

Cards are presentation components.

A database record should automatically qualify for the appropriate card presentation.

---

# 30. AI AND BREADCRUMBS

AI should not manually create breadcrumb text.

Breadcrumbs should be derived from database relationships.

---

# 31. AI AND SEARCH

When a record is created or updated, the search system should eventually recognize the change.

If a separate search index exists, it should be updated or rebuilt from the database.

---

# 32. AI AND MEDIA

AI may assist with:

- Selecting images
- Associating images
- Generating captions
- Suggesting alt text
- Identifying duplicate media

Media remains a structured record.

---

# 33. MEDIA VERIFICATION

Do not assume an image is accurate simply because AI identifies it.

The administrator should be able to verify:

- Identity
- Source
- Usage rights
- Caption
- Attribution

where appropriate.

---

# 34. AI AND SOURCES

AI should preserve source URLs and references when available.

Do not reduce source information to:

"According to the internet."

Use structured source records.

---

# 35. AI AND SOURCE CONFIDENCE

Where appropriate, AI should distinguish:

Direct source

from:

Secondary source

from:

AI inference

from:

Unverified information.

---

# 36. AI AND REAL PEOPLE

Information about real people should receive appropriate verification.

Avoid automatically publishing:

- Allegations
- Unverified accusations
- Sensitive claims
- Speculative information

The administrator should have review control.

---

# 37. AI AND FICTIONAL SAMPLE DATA

For demonstration content, AI may create fictional records.

However, fictional records must be clearly identified as:

SAMPLE

DEMONSTRATION

or:

FICTIONAL

They should not be presented as real public officials or real organizations.

---

# 38. AI AND ILLINOIS

API Group is Illinois-focused.

AI should prioritize Illinois relevance when organizing the collection.

Federal records may be included when they materially affect Illinois.

State records should focus on Illinois.

County, city, village, and civic records should maintain their Illinois relationships.

---

# 39. FEDERAL RECORDS

Federal records should not automatically become nationwide records merely because they are federal.

The system should capture why the federal record is relevant to Illinois where appropriate.

Possible relationships:

Federal Agency
→ Illinois Program

Federal Agency
→ Illinois Funding

Federal Agency
→ Illinois Grant

Federal Agency
→ Illinois Jurisdiction

---

# 40. STATE RECORDS

State records should be associated with Illinois.

The system should support internal state organizational structures.

Example:

Illinois Agency
→ Division
→ Bureau
→ Office
→ Program

---

# 41. COUNTY RECORDS

County records should connect to Illinois.

County agencies should connect to the appropriate county.

County personnel should connect to agencies or jurisdictions as appropriate.

---

# 42. CITY AND VILLAGE RECORDS

Cities and villages should be connected to:

- County
- Illinois
- Agencies
- Personnel
- Civic organizations
- Articles

where appropriate.

---

# 43. CIVIC RECORDS

Civic organizations should be independently represented.

AI should not assume every civic organization is a government agency.

---

# 44. PERSONNEL INDEPENDENCE

AI must preserve personnel independence.

A person may have:

- Current agency
- Former agency
- Multiple agency relationships
- Civic relationships
- Article relationships

Do not create duplicate personnel profiles simply because the person appears in multiple contexts.

---

# 45. RECORD MERGING

The system should eventually support merging duplicate records.

Example:

Person A

and:

Person A (duplicate)

can be reviewed and merged into one canonical record.

Relationships should be transferred appropriately.

---

# 46. RECORD SPLITTING

Where one record incorrectly combines two different entities, the system should support separation.

This is important for:

- People with identical names
- Agencies with similar names
- Organizations with similar names

---

# 47. RECORD HISTORY

Changes should be traceable.

Where feasible, preserve:

- Previous value
- New value
- Date
- Administrator
- AI action
- Source

---

# 48. AI AUDIT TRAIL

AI-generated changes should be identifiable.

The system should record, where appropriate:

- AI-assisted creation
- AI-assisted update
- Human approval
- Date
- Source information

---

# 49. FAILED OPERATIONS

If AI cannot confidently complete an operation, it should not fabricate missing information.

It should instead leave the record:

- In draft
- In review
- Incomplete

and identify what needs attention.

---

# 50. MISSING INFORMATION

Missing data should remain missing.

Do not invent:

- Addresses
- Phone numbers
- Personnel positions
- Agency relationships
- Sources
- Dates

to make a record look complete.

---

# 51. DATA CONFIDENCE

Where useful, records may contain confidence or verification metadata.

This should not replace source documentation.

Confidence is a workflow aid, not proof.

---

# 52. AUTOMATIC FRONTEND PROPAGATION

Once a record is approved:

DATABASE RECORD
↓
DIRECTORY
↓
SIDEBAR
↓
SEARCH
↓
CARDS
↓
RELATED RECORDS
↓
PROFILE PAGE

should update automatically as appropriate.

---

# 53. NO MANUAL PAGE CREATION

Adding an ordinary record should not require creating a new page manually.

The system should generate the profile page from the appropriate template and record.

---

# 54. NO MANUAL MENU CREATION

Adding an ordinary hierarchy record should not require adding a new menu item manually.

Database-driven navigation should discover the record.

---

# 55. NO MANUAL CARD CREATION

Adding an ordinary category or record should not require creating a new card manually.

The appropriate card component should render it.

---

# 56. ADMINISTRATOR EDITOR

The editor should expose the structured fields appropriate to each record type.

For an agency:

- Name
- Type
- Description
- Jurisdiction
- Website
- Image
- Personnel
- Related records
- Sources

For a person:

- Name
- Photograph
- Position
- Relationships
- Biography
- Sources

For an article:

- Title
- Body
- Image
- Category
- Dependency
- Tags
- Sources
- Related records

---

# 57. FORM DESIGN

Forms should be understandable.

Use:

"Parent Agency"

instead of:

"parent_entity_id"

The database field may use the technical identifier internally.

The administrator should see human-readable labels.

---

# 58. RELATIONSHIP SELECTORS

Administrators should be able to search for related records.

Example:

Related Agency:
[Search agencies...]

Related Person:
[Search personnel...]

Related County:
[Search jurisdictions...]

Do not force administrators to know internal IDs.

---

# 59. RELATIONSHIP AUTOCOMPLETE

Where appropriate, relationship fields should provide autocomplete.

Example:

Type:

"Attorney"

Possible records appear.

The administrator selects the canonical record.

---

# 60. IMAGE SELECTION

Administrators should be able to select an existing media record or upload a new image.

Do not require file paths or coding.

---

# 61. PREVIEW

Administrators should be able to preview records before publishing.

Preview should show approximately how the record will appear publicly.

---

# 62. DRAFTS

Records should support drafts.

This is especially important for AI-generated information.

---

# 63. PUBLISHING

Publishing should make a record publicly available.

The system should automatically update relevant database-driven displays.

---

# 64. UNPUBLISHING

Administrators should be able to remove a record from public displays without necessarily deleting it.

---

# 65. ARCHIVING

Archived records should remain available for administrative purposes where appropriate.

They should normally be excluded from ordinary public lists.

---

# 66. AI BULK IMPORT

The system should eventually support AI-assisted bulk ingestion.

Example:

Import information for multiple agencies.

AI should:

- Identify records
- Check duplicates
- Prepare structured data
- Establish relationships
- Identify missing sources
- Prepare review queue

Do not publish an entire bulk import blindly.

---

# 67. BULK REVIEW

Administrators should be able to review multiple proposed records efficiently.

Possible actions:

- Approve
- Reject
- Edit
- Assign category
- Assign jurisdiction
- Publish

---

# 68. DATA QUALITY DASHBOARD

A future administrative dashboard should identify:

- Missing descriptions
- Missing images
- Missing sources
- Duplicate candidates
- Orphaned relationships
- Invalid hierarchy
- Unpublished drafts
- Unverified records

---

# 69. AI DATA QUALITY ASSISTANCE

AI may assist with identifying:

- Duplicate records
- Missing fields
- Inconsistent names
- Broken relationships
- Missing sources
- Potential classification errors

AI should suggest corrections rather than silently changing important information.

---

# 70. TAXONOMY MANAGEMENT

Administrators should be able to manage:

- Categories
- Subcategories
- Dependencies
- Record types

without coding.

AI may assist but should not make taxonomy changes silently.

---

# 71. CATEGORY CREATION

Creating a category should automatically make it available to appropriate:

- Navigation
- Sidebars
- Cards
- Search
- Breadcrumbs

where applicable.

---

# 72. DEPENDENCY CREATION

Creating a dependency should automatically make it available beneath its parent.

No template modification should be required.

---

# 73. RELATIONSHIP CREATION

Creating a relationship should automatically make appropriate related-record displays aware of it.

Example:

Connect Person A to Agency B.

Agency B's personnel display should recognize Person A.

Person A's agency relationships should recognize Agency B.

---

# 74. RELATIONSHIP REMOVAL

Removing a relationship should remove that relationship from appropriate displays without deleting either canonical record.

---

# 75. DATABASE CONSISTENCY

The application should prevent invalid references.

Do not allow a relationship to point to a nonexistent record.

---

# 76. PORTABILITY

AI-assisted records must remain portable.

AI should never solve a data problem by placing information only into:

- A page builder
- A template
- Static HTML
- CSS
- JavaScript
- A proprietary visual component

The information belongs in the database.

---

# 77. EXPORT AFTER AI INGESTION

A record created by AI should be just as exportable as a record created manually.

The origin of the record must not affect portability.

---

# 78. AI MODEL INDEPENDENCE

The collection should not become dependent upon one particular AI model.

A future AI system should be able to understand the same structured records.

---

# 79. HUMAN EDITORIAL INDEPENDENCE

The administrator should not be forced to use AI.

Everything AI can create should also be manageable manually where practical.

---

# 80. AI IS AN ASSISTANT

AI should accelerate:

- Research
- Organization
- Data entry
- Classification
- Relationship discovery
- Content preparation

AI should not replace:

- Data ownership
- Editorial judgment
- Administrative authority
- Source verification
- Portability requirements

---

# 81. MONSTER NEWS SEPARATION

AI workflows for API Group and Monster News must respect their independent domains.

AI may use API Group records while preparing Monster News content.

However:

Monster News articles belong to Monster News.

API Group profiles belong to API Group.

---

# 82. CROSS-SYSTEM REFERENCES

If a Monster News article references an API Group record, use a structured cross-system reference.

Do not duplicate the entire API Group profile into the Monster News article.

---

6. Confirm search recognizes it.
7. Open its profile.
8. Add a person.
9. Confirm the relationship appears.
10. Export the records.
11. Confirm the data remains structured.

---

# 84. AI CHANGE TEST

Test:

1. Give AI information about a new agency.
2. AI searches for duplicates.
3. AI prepares the record.
4. AI identifies relationships.
5. AI records sources.
6. Administrator reviews.
7. Administrator approves.
8. Record becomes public.
9. Website updates automatically.
10. Export remains possible.

---

# 85. PORTABILITY TEST

For every major AI-assisted operation, verify:

Can the resulting data be exported?

Can another system understand it?

Can another AI understand it?

Can the website be replaced without losing the collection?

If the answer is unclear, stop and correct the architecture.

---

# 86. FAILURE CONDITION

The implementation fails this specification if:

- AI must edit code to create ordinary records.
- Administrators must edit code to add records.
- Sidebars require manual hard-coded updates.
- Cards require manual hard-coded updates.
- Breadcrumbs require manual hard-coded updates.
- New categories require template changes.
- New agencies require template changes.
- New personnel require template changes.
- Relationships exist only as prose.
- Data cannot be exported.
- The CMS becomes the only copy of the information.

---

# 87. SUCCESS CONDITION

The implementation succeeds when:

A nontechnical administrator can add a record.

The database stores it.

The hierarchy recognizes it.

Navigation recognizes it.

The sidebar recognizes it.

Search recognizes it.

Cards recognize it.

Relationships recognize it.

The profile page renders it.

The data can be exported.

No code was required.

# 89. FINAL PRINCIPLE

The administrator should be able to think:

"I found something new."

and then:

"Put it into API Group."

The system should handle the technical consequences.

The administrator should not have to think:

"What page do I edit?"

"What menu do I change?"

"What sidebar do I modify?"

"What card do I add?"

"What template do I change?"

Those are implementation details.

The administrator manages the information.

The system manages the presentation.

---

# 90. GOLDEN RULE

Before any AI-assisted operation:

1. Confirm the information belongs in API Group.
2. Confirm the appropriate record type.
3. Search for an existing canonical record.
4. Preserve existing relationships.
5. Add structured data.
6. Preserve sources.
7. Preserve media references.
8. Allow appropriate human review.
9. Confirm the frontend reflects the database.
10. Confirm the resulting data remains portable.

Never sacrifice portability for convenience.

**PORTABILITY MUST BE PRESERVED.**

After making changes, verify the result and explicitly state:

**PORTABILITY CONFIRMED.**
