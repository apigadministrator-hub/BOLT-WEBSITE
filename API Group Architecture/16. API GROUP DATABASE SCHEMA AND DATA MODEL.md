# API GROUP DATABASE SCHEMA AND DATA MODEL

## PURPOSE

This document defines the database architecture required to support the API Group website.

The API Group website must be database-driven.

The database is the source of truth for:

- Profiles
- Agencies
- Personnel
- Jurisdictions
- Counties
- Cities
- Villages
- Civic organizations
- Categories
- Subcategories
- Dependencies
- Articles
- Sources
- Tags
- Images
- Relationships
- Navigation
- Featured content
- Sidebar content
- Searchable records
- Metadata

The website is a presentation layer over this structured collection.

---

# 1. DATABASE-FIRST PRINCIPLE

Do not build the website around static pages.

Build the website around structured records.

The intended architecture is:

DATABASE
↓
STRUCTURED RECORDS
↓
RELATIONSHIPS
↓
QUERIES
↓
PAGE TEMPLATES
↓
WEBSITE

A database record should be capable of being displayed in multiple places without being duplicated.

---

# 2. SOURCE OF TRUTH

The database is the authoritative source for API Group information.

The frontend should not contain authoritative copies of:

- Agency names
- Personnel names
- County names
- City names
- Village names
- Civic organization names
- Category names
- Dependency names
- Article metadata
- Sidebar links

These should be retrieved from the database.

---

# 3. RECORD IDENTITY

Every major record should have a unique stable identifier.

Examples:

- agency_id
- person_id
- jurisdiction_id
- organization_id
- category_id
- dependency_id
- article_id
- source_id
- media_id

Identifiers should remain stable when the record's display name changes.

---

# 4. RECORD TYPES

The database should distinguish between different types of records.

Initial record types include:

- Agency
- Personnel
- Jurisdiction
- Civic Organization
- Category
- Dependency
- Article
- Source
- Media
- Tag

Additional record types may be added later.

The architecture must not prevent expansion.

---

# 5. AGENCY RECORD

An agency record should support fields such as:

- ID
- Name
- Description
- Agency type
- Jurisdiction
- Parent agency
- Address
- Website
- Contact information where appropriate
- Logo/media
- Status
- Created date
- Modified date

An agency may have relationships with many other records.

---

# 6. AGENCY TYPE

Agency type should be structured data.

Initial types include:

- Federal
- State
- County
- City
- Village
- Civic

The administrator must be able to add additional types if required.

Do not assume the initial list is permanent.

---

# 7. PERSONNEL RECORD

A personnel record should support:

- ID
- Name
- Preferred display name
- Photograph
- Title
- Biography
- Contact information where appropriate
- Status
- Created date
- Modified date

A personnel record should not contain a permanent single-agency ownership assumption.

---

# 8. PERSON-AGENCY RELATIONSHIP

A person may be associated with multiple agencies.

Therefore:

PERSON
↕
PERSON-AGENCY RELATIONSHIP
↕
AGENCY

The relationship itself may contain:

- Position
- Role
- Start date
- End date
- Current status
- Notes
- Source

This allows personnel history to be represented without duplicating people.

Examples:

- United States
- Illinois
- County

- Village

Example:

United States
→ Illinois
→ County
→ City

# 12. VILLAGE RECORD

# 13. CIVIC ORGANIZATION RECORD

- Organization type

- Address

- Contact information where appropriate

# 14. CATEGORY RECORD

- Description

# 15. DEPENDENCY RECORD

---

# 16. HIERARCHICAL RECORD MODEL

The system should support arbitrary parent-child relationships.

Conceptually:

PARENT
→ CHILD
→ CHILD
→ CHILD

A child may itself become a parent.

This supports:

Category
→ Subcategory
→ Dependency
→ Dependency
→ Dependency

without requiring a schema redesign for every additional level.

---

# 17. SELF-REFERENCING HIERARCHY

Where practical, hierarchical content should use a parent identifier.

Example:

parent_id

A record with no parent may represent a root.

A record with a parent may represent a child.

This permits expandable trees without hard-coded levels.

---

# 18. API GROUP ROOT

API Group should have a root-level identity.

The root should not need to be duplicated on every child record.

Relationships should establish where records belong.

---

# 19. ARTICLE RECORD

- ID
- Title
- Subtitle
- Summary
- Body
- Featured image
- Author
- Publication date
- Modified date
- Status
- Featured flag
- Category
- Dependency
- Slug

Additional metadata should be extensible.

---

# 20. ARTICLE-RECORD RELATIONSHIPS

Articles should be able to reference structured API Group records.

Examples:

Article

Article

Article
→ County

Article
→ City

Article
→ Village

Article
→ Civic Organization

These should be relationships rather than duplicated profile information.

---

# 21. SOURCE RECORD

Sources should be structured records.

A source may contain:

- ID
- Name
- URL
- Description
- Publication
- Date
- Document reference
- Source type
- Notes

Sources may be connected to:

- Articles
- Agencies

- Jurisdictions
- Civic organizations
- Other records

# 22. MEDIA RECORD

Images and other media should be represented as structured media records where practical.

A media record may include:

- ID
- File reference
- Filename
- Title
- Caption
- Alt text
- Source
- Credit
- Media type
- Created date
- Modified date

Media should not be permanently embedded into arbitrary page templates.

---

# 23. TAG RECORD

Tags should be database records.

A tag should support:

- ID
- Name
- Description
- Slug
- Status

Tags may be connected to many articles and other appropriate records.

---

# 24. MANY-TO-MANY RELATIONSHIPS

The database must support many-to-many relationships.

Examples:

One person
→ many agencies

One agency
→ many personnel

One article
→ many agencies

One agency
→ many articles

One person
→ many articles

One article
→ many sources

One source
→ many articles

Do not solve these relationships by duplicating entire records.

---

# 25. RELATIONSHIP RECORDS

Where a relationship contains meaningful information, represent the relationship itself as a structured record.

Example:

PERSON
→ AGENCY RELATIONSHIP
→ AGENCY

The relationship may contain:

- Role
- Position
- Dates
- Status
- Notes
- Source

---

# 26. CANONICAL RECORDS

Every entity should have one canonical record whenever practical.

For example:

One person should have one personnel record.

One agency should have one agency record.

One county should have one county record.

Other pages should reference the canonical record.

---

# 27. NO DUPLICATE PROFILES

Do not create separate personnel records simply because the person appears under:

- Federal
- State
- County
- City
- Village
- Civic

The person remains one canonical record.

Relationships determine where the person appears.

---

# 28. DATABASE-DRIVEN NAVIGATION

Navigation must be generated from database records.

Example:

If there are:

3 county records

the county navigation contains 3 records.

If there are:

102 county records

the county navigation contains 102 records.

Do not hard-code a predetermined count.

---

# 29. DATABASE-DRIVEN SIDEBARS

Sidebars should query the database.

For example:

Agency Profiles
→ State
→ Illinois agencies

The sidebar should display the state agency records available in the database.

Adding a new agency should automatically make it available to the relevant sidebar.

---

# 30. DATABASE-DRIVEN CARDS

Cards should be generated from records.

A category card should be created from:

Category record

An agency card should be created from:

Agency record

A personnel result should be created from:

Personnel record

Do not manually create each card.

---

# 31. DATABASE-DRIVEN BREADCRUMBS

Breadcrumbs should be generated from parent-child relationships.

Example:

API Group
→ Agency Profiles
→ State
→ Illinois
→ Agency

The breadcrumb should reflect the actual database hierarchy.

---

# 32. DATABASE-DRIVEN SEARCH

Search should operate on structured records.

Searchable fields may include:

- Name
- Title
- Description
- Record type
- Jurisdiction
- Category
- Dependency
- Tags
- Source
- Article content

Search should return canonical records.

---

# 33. FILTERING

The database architecture should support filtering by:

- Record type
- Jurisdiction
- Agency type
- Category
- Dependency
- Person
- Date
- Tag
- Status

Additional filters may be added later.

---

# 34. SORTING

Records should support configurable sorting.

Examples:

- Alphabetical
- Newest
- Oldest
- Featured
- Manual sort order
- Relevance

---

# 35. STATUS

Major records should support status.

Possible values include:

- Draft
- Published
- Hidden
- Archived

Additional statuses may be added.

---

# 36. SOFT DELETION

Where appropriate, records should support archiving or soft deletion rather than immediate physical deletion.

This protects relationships and historical data.

Permanent deletion should be an intentional administrative action.

---

# 37. AUDIT INFORMATION

Major records should maintain:

- Created date
- Modified date
- Created by
- Modified by

Where feasible, maintain revision history.

This is especially important for profiles and editorial records.

---

# 38. REVISION HISTORY

The system should support historical revisions where practical.

An administrator should be able to determine:

- What changed
- When it changed
- Who changed it

The implementation should avoid destroying useful historical information.

---

# 39. AI DATA INGESTION

The database must be designed so AI can eventually create and update records.

AI should be able to provide structured information such as:

Name
Description
Type
Parent
Relationships
Image
Sources

The system should validate the information before committing it.

---

# 40. AI MUST SEARCH BEFORE CREATING DUPLICATES

Before creating a new record, AI should determine whether an equivalent record already exists.

Example:

If "Sample County" already exists, do not automatically create another "Sample County."

Instead:

1. Search.
2. Compare.
3. Determine whether the existing record is the intended entity.
4. Update or relate the existing record when appropriate.
5. Create a new record only when justified.

---

# 41. AI RECORD CREATION WORKFLOW

Recommended workflow:

INPUT
↓
IDENTIFY RECORD TYPE
↓
SEARCH EXISTING RECORDS
↓
CHECK FOR DUPLICATE
↓
VALIDATE DATA
↓
CREATE OR UPDATE RECORD
↓
CREATE RELATIONSHIPS
↓
SAVE SOURCES
↓
UPDATE SEARCH INDEX
↓
FRONTEND AUTOMATICALLY REFLECTS CHANGE

---

# 42. HUMAN APPROVAL

AI-created information should support an approval workflow where appropriate.

Possible states:

AI Draft
→ Human Review
→ Approved
→ Published

The exact workflow may evolve.

---

# 43. AI SHOULD NOT EDIT TEMPLATES

AI should generally modify structured data.

AI should not need to edit:

- HTML templates
- CSS
- Navigation code
- Sidebar code
- Card templates

to add ordinary records.

---

# 44. ADMINISTRATOR DATA ENTRY

A nontechnical administrator should be able to create records manually.

The administrator should be able to:

- Add agency
- Add person
- Add county
- Add city
- Add village
- Add civic organization
- Add category
- Add dependency
- Add article
- Add source
- Upload image
- Create relationships

without coding.

---

# 45. AUTOMATIC FRONTEND UPDATE

After saving a record:

DATABASE
↓
WEBSITE

The appropriate pages should recognize the new record automatically.

For example:

Add county.

Save.

County directory updates.

Sidebar updates.

Search updates.

Related records update.

No template modification.

---

# 46. SIDEBAR CONTENT IS NOT A STATIC MENU

A database-driven sidebar should not be treated as a manually maintained menu.

Where the sidebar represents a hierarchy, it should query the hierarchy.

This ensures that adding a record automatically makes it discoverable.

---

# 47. MANUAL SIDEBAR CONTENT

The system may also support manually selected sidebar content.

This is separate from automatically generated hierarchy navigation.

An administrator may intentionally add:

- Custom links
- Promotional content
- Featured records
- Related records
- Information blocks

without changing the underlying hierarchy.

---

# 48. HIERARCHY VS NAVIGATION

Do not confuse:

DATABASE HIERARCHY

with:

VISUAL NAVIGATION.

The hierarchy determines relationships.

The navigation determines how those relationships are presented to users.

The same hierarchy may be presented:

- In a sidebar
- In breadcrumbs
- As cards
- As lists
- In search results

---

# 49. HIERARCHY VS PROFILE

A profile is a record.

A hierarchy is a relationship between records.

A person can appear in multiple places without becoming multiple people.

An agency can appear in multiple lists without becoming multiple agencies.

---

# 50. EXTENSIBLE FIELDS

The data model should permit additional fields to be introduced later.

Do not design the system so that adding one new attribute requires rebuilding the entire application.

However, avoid uncontrolled arbitrary fields when a structured field is more appropriate.

---

# 51. STRUCTURED DATA OVER FREE TEXT

Use structured fields for information that will be:

- Searched
- Filtered
- Sorted
- Related
- Displayed in multiple places

Examples:

Agency type should be structured.

Jurisdiction should be structured.

Person relationships should be structured.

Tags should be structured.

Sources should be structured.

---

# 52. FREE TEXT

Use free text where information is primarily explanatory.

Examples:

- Biography
- Description
- Notes
- Article body

Do not force narrative information into artificial structured fields.

---

# 53. URLS

Important external URLs should be stored as structured fields where appropriate.

Examples:

- Agency website
- Organization website
- Source URL

URLs should not be buried permanently in article text when they need to be queried or displayed independently.

---

# 54. IMAGES

Image references should be reusable.

One image may be displayed in:

- Profile
- Card
- Search result
- Related record
- Article

without requiring duplicate file storage.

---

# 55. IMAGE REPLACEMENT

Replacing a record's image should update appropriate displays automatically.

The frontend should retrieve the current media reference from the database.

---

# 56. DATA VALIDATION

The system should validate important fields.

Examples:

- Required name
- Valid record type
- Valid parent relationship
- Valid image reference
- Valid source URL
- Valid relationship target

---

# 57. CIRCULAR HIERARCHIES

The system should prevent invalid hierarchy relationships.

For example:

A cannot be the parent of B if B is already an ancestor of A.

The administrator interface should prevent accidental circular structures.

---

# 58. ORPHAN RECORDS

The system should identify records that have lost required relationships.

For example:

A dependency whose parent category was removed.

A city whose required jurisdiction relationship is missing.

An article whose required category was deleted.

These conditions should be detectable.

---

# 59. RELATIONSHIP INTEGRITY

Deleting or archiving a record must not silently destroy unrelated records.

The system should identify dependent relationships before destructive actions.

---

# 60. DATABASE MIGRATION

The database should be capable of evolving.

Future schema changes should be performed through migrations or another controlled versioning mechanism.

Do not rely on manually changing production database structures without a record of the change.

---

# 61. BACKUP

The database must be backed up regularly.

Backups should include:

- Structured records
- Relationships
- Metadata
- Appropriate media references

Backup strategy should be documented separately.

---

# 62. EXPORT

The system must support export of structured API Group data.

At minimum, the architecture should permit export of:

- Records
- Relationships
- Categories
- Dependencies
- Articles
- Tags
- Sources
- Metadata

Media should be exportable or separately transferable.

---

# 63. PORTABILITY

The database must not become permanently dependent upon one CMS.

The data should remain understandable outside the website.

Where practical, use portable formats and documented structures.

---

# 64. DATABASE ACCESS

Application code should access the database through a controlled data layer.

Do not scatter raw database assumptions throughout page templates.

The presentation layer should request records through defined application interfaces.

---

# 65. PRESENTATION LAYER

Templates should receive structured data.

Example:

Template receives:

Agency record
+
Related personnel
+
Related articles
+
Sources

The template decides how to display them.

The template should not determine whether the agency exists.

---

# 66. DATA LAYER

The data layer should determine:

- What records exist
- What relationships exist
- What records match a query
- What records are children of a parent
- What records are featured
- What records are latest

---

# 67. ADMINISTRATION LAYER

The administration interface should provide:

- CRUD operations
- Relationship management
- Hierarchy management
- Media management
- Publishing controls
- Search
- Filtering
- Revision management
- AI-assisted creation where implemented

CRUD means:

Create
Read
Update
Delete

---

# 68. SEARCH INDEX

If a separate search index is used, it should be considered a derived system.

The database remains the source of truth.

If the search index is rebuilt, it should be possible to reconstruct it from the database.

---

# 69. CACHING

Caching may be used for performance.

However, cached content must remain derived from the database.

A cache should never become the only copy of a record.

---

# 70. FRONTEND PERFORMANCE

Large collections may require:

- Pagination
- Lazy loading
- Search
- Filtering
- Compact result layouts
- Caching

Do not attempt to load thousands of records into a single page unnecessarily.

---

# 71. LARGE PERSONNEL COLLECTIONS

Personnel lists should use compact displays.

A typical directory result may include:

[Thumbnail] Name — Position — Organization

The full profile is opened only when selected.

---

# 72. LARGE AGENCY COLLECTIONS

Agency directories may use:

- Cards
- Compact lists
- Search
- Filters

The presentation should be configurable.

---

# 73. LARGE JURISDICTION COLLECTIONS

County, city, and village directories should support scalable navigation.

Do not design the interface around a small demonstration count.

# 81. API GROUP DATABASE PRINCIPLE

The database should be capable of becoming much larger than the initial demonstration.

The architecture must not be optimized only for:

- A few agencies
- A few people
- A few counties
- A few articles

It should be designed as a growing collection.

---

# 82. AI-READY PRINCIPLE

The database should be understandable to both humans and AI systems.

Records should have:

- Stable identifiers
- Explicit types
- Explicit relationships
- Clear names
- Structured fields
- Source references
- Machine-readable metadata

Avoid storing critical relationships only as prose.

---

# 83. HUMAN-READABLE PRINCIPLE

The database should also remain understandable to humans.

Documentation should explain:

- Record types
- Fields
- Relationships
- Hierarchy
- Identifiers
- Export format

---

# 84. MONSTER NEWS SEPARATION

Monster News has its own database/content domain.

Do not merge Monster News article ownership into API Group.

API Group may be referenced by Monster News.

Monster News may reference API Group records.

But the systems remain independent.

---

# 85. CROSS-SYSTEM REFERENCES

If cross-system references are implemented, they should use stable identifiers or another documented relationship mechanism.

Example:

Monster News Article
→ references
→ API Group Agency ID

This is preferable to copying the entire agency record.

---

# 86. DATABASE DOMAIN SEPARATION

At minimum, maintain a clear conceptual separation between:

API GROUP DATA

and:

MONSTER NEWS DATA

Even if the implementation uses one physical database, the application should maintain clear ownership boundaries.

---

# 87. FUTURE DATABASE EXPANSION

The architecture should allow future additions such as:

- Documents
- Meetings
- Grants
- Programs
- Campaigns
- Projects
- Events
- Contracts
- Vendors
- Additional civic entities

These should be added as structured record types when justified.

# 88. DO NOT OVERDESIGN THE FIRST VERSION

The initial implementation should establish a solid foundation.

Do not create hundreds of unnecessary tables merely because they might someday be useful.

Start with the records and relationships required for the working demonstration.

Design for extension.

---

# 91. GOLDEN RULE

Before implementing a database feature, ask:

Is this information structured?

Can it be searched?

Can it be related?

Can it be exported?

Can it be moved?

Can AI understand it?

Can another application understand it?

If not, reconsider the design.

The database is not merely a storage mechanism for the website.

The database is the portable collection.

The website is one interface to that collection.

**PORTABILITY MUST BE PRESERVED.**

After making any database or architecture change, verify that the change did not create unnecessary coupling or destroy portability.
