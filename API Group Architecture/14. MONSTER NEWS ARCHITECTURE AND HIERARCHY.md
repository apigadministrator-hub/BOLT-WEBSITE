# MONSTER NEWS ARCHITECTURE AND HIERARCHY

## PURPOSE

Monster News is an independent news publication and content system.

It is not a section, category, dependency, or child system of API Group.

Monster News must have its own:

- Root category
- Content hierarchy
- Categories
- Dependencies
- Articles
- Article templates
- Images
- Navigation
- Search
- Featured content
- Latest content
- Administrative controls
- Editorial controls
- Database records
- Control panel

Monster News may reference information maintained by API Group when useful, but the two systems must remain independently manageable.

---

# 1. THE MONSTER NEWS ROOT

The top-level hierarchy begins with:

MONSTER NEWS

Monster News is the root content category for the Monster News publication.

The Monster News root record must have:

- Name
- Description
- Image
- Logo/branding
- Slug or stable identifier
- Status
- Created date
- Modified date

The root record should be editable through the administrator interface.

Do not hard-code the Monster News description or image into the frontend.

---

# 3. INITIAL DEFAULT NEWS CATEGORIES

The initial demonstration should create at least these three default Monster News categories:

## FLASH NEWS

Description:

Short, timely updates and developing information intended for rapid publication when information is current and readers need to know what is happening.

---

## IN THE NEWS TODAY

Description:

A daily-oriented collection of noteworthy developments, public announcements, government activity, community matters, and other news relevant to Illinois readers.

---

## INVESTIGATIONS

Description:

Longer-form reporting focused on matters of public interest, accountability, government activity, public spending, records, institutions, organizations, and issues affecting Illinois communities.

---

# 4. DEFAULT CATEGORIES ARE NOT PERMANENT

The three initial categories are starting points.

They must not be hard-coded as the permanent Monster News taxonomy.

The administrator must be able to:

- Add categories
- Rename categories
- Edit descriptions
- Change images
- Change category order
- Hide categories
- Archive categories
- Delete categories where appropriate
- Create additional categories

There must be no artificial limit of three categories.

---

# 5. CATEGORY RECORDS

Every Monster News category should be a database record.

A category should support:

- Unique ID
- Name
- Description
- Image
- Parent
- Slug
- Sort order
- Status
- Created date
- Modified date

The frontend should render category information from the database.

---

# 6. CATEGORY CARDS

Monster News category cards should be generated from database records.

A category card may display:

- Image
- Category name
- Description
- Article count
- Link

If a new category is created in the administrator interface, it should automatically become available to the appropriate category-card display.

No template modification should be required.

For example:

# 11. INFINITE EXPANSION PRINCIPLE

The hierarchy should be considered expandable without a predetermined endpoint.

- One category
- Ten categories
- One hundred categories

and:

- One dependency
- Ten dependencies
- Multiple levels of dependencies

The number of records is determined by the database.

Required operations:

- Create
- Read
- Edit
- Rename

- Publish
- Hide
- Archive
- Delete where appropriate

- Root content
- Categories

- Articles

# 13. MONSTER NEWS ARTICLE OWNERSHIP

Monster News articles belong to Monster News.

An article should have a Monster News content owner/domain.

An article may belong to:

- A Monster News category
- A Monster News dependency
- Additional child dependencies

The article should remain an independent database record.

---

A Monster News article should support:

- Article ID
- Headline
- Subheadline
- Summary
- Body
- Featured image
- Additional images
- Author
- Publication date
- Modification date
- Category
- Dependency
- Tags
- Sources
- Related records
- Featured status
- Latest status

# 15. ARTICLE IMAGES

Images are an integral part of Monster News.

Articles must support:

- Featured image
- Inline images
- Image captions
- Alt text
- Image source
- Image metadata where appropriate

Images must be stored and managed independently from article text wherever practical.

---

# 16. CATEGORY IMAGES

Categories must support images.

The administrator should be able to select or replace a category image.

Category images may be displayed on:

- Landing pages
- Category cards
- Navigation
- Search results
- Category headers

---

# 17. DEPENDENCY IMAGES

Dependencies should also support images.

This allows a dependency to have a visual identity when the design calls for it.

The administrator should be able to change the dependency image without editing code.

---

# 18. FEATURED NEWS

Monster News must support featured content.

An administrator may mark an article as:

FEATURED

Featured articles should automatically become eligible for display in the Monster News featured-news area.

The administrator should not need to manually copy an article into a featured page.

The featured section should query the database.

---

# 19. LATEST NEWS

Monster News must support a latest-news display.

Latest news should be generated from article publication data.

When a new article is published, it should automatically become eligible for the latest-news display.

The number of displayed articles should be configurable.

---

# 20. ARTICLE CARDS

Article cards may display:

- Featured image
- Headline
- Summary
- Category
- Date
- Author
- Optional metadata

Cards must be generated from database records.

# 21. LARGE ARTICLE COLLECTIONS

Large collections should not require every article to appear as a large visual card.

Monster News should support:

- Cards
- Compact lists
- Search results
- Pagination
- Filtering

The presentation should depend on context.

# 25. BREADCRUMBS

Monster News pages should preserve the user's position in the hierarchy.

Example:

Monster News
→ Investigations
→ Public Accountability
→ Government Spending
→ Sample Article

Another example:

Monster News
→ Flash News
→ Breaking Updates
→ Sample Article

Breadcrumbs must be generated from the database hierarchy.

---

# 26. SIDEBAR NAVIGATION

Monster News should support an optional left sidebar.

The sidebar should be database-driven.

For example, on a Monster News category page, the sidebar may show:

Flash News
In the News Today
Investigations
Additional Categories

When the user enters a category, the sidebar may change to show that category's dependencies.

Example:

Investigations
→ Public Accountability
→ Government & Spending
→ Additional Dependencies

The sidebar is contextual navigation.

---

# 27. OPTIONAL RIGHT SIDEBAR

Monster News should also support an optional right sidebar.

The administrator should be able to decide whether a page uses:

- Left sidebar
- Right sidebar
- Both
- Neither

The right sidebar may contain:

- Related articles
- Featured articles
- Related API Group records
- Sources
- Links
- Other administrator-selected content

---

# 28. SIDEBAR CONTENT MANAGEMENT

An administrator without coding experience should be able to manage sidebar content.

The administrator should be able to:

- Enable or disable a sidebar
- Select its location
- Add links
- Remove links
- Reorder links
- Select database-driven content
- Add custom content where appropriate

Sidebar configuration must not require editing templates.

---

# 29. DATABASE-DRIVEN NAVIGATION

Monster News navigation must come from the database.

If the database contains three categories, the navigation should show those three.

If the administrator creates a fourth category, the navigation should automatically recognize it.

The same principle applies to dependencies.

---

# 30. SEARCH

Monster News should have its own search experience.

Search should be capable of finding:

- Articles
- Categories
- Dependencies
- Tags
- Other appropriate Monster News content

Search should return canonical records.

---

# 31. SEARCH AND API GROUP

Monster News search and API Group search should remain logically independent.

Do not automatically mix the two collections.

If cross-system search is eventually desired, it should be an intentional feature.

---

# 32. API GROUP REFERENCES

Monster News may reference API Group information.

For example:

A Monster News article may reference an API Group agency profile.

A Monster News article may reference an API Group personnel profile.

A Monster News article may reference an API Group civic organization.

A Monster News article may reference an API Group jurisdiction.

These should be relationships or references.

They should not require duplicating the complete API Group record inside Monster News.

---

# 33. API GROUP DOES NOT BECOME MONSTER NEWS

The existence of an API Group reference does not change the ownership of a Monster News article.

Monster News remains the owner of its article.

API Group remains the owner of its profile.

The two systems may reference one another without becoming one system.

---

# 34. CANONICAL API GROUP RECORDS

When Monster News references API Group information, it should point to the canonical API Group record where possible.

Do not create unnecessary duplicate copies.

Example:

MONSTER NEWS ARTICLE
→ references
→ API GROUP AGENCY RECORD

not:

MONSTER NEWS ARTICLE
→ creates duplicate agency profile

---

# 35. API GROUP INFORMATION IN NEWS ARTICLES

API Group information may be incorporated into Monster News presentations where appropriate.

Examples:

- Agency name
- Agency profile link
- Personnel name
- Personnel profile link
- Jurisdiction
- Related civic organization
- Related source
- Related article

This information should be pulled from the appropriate canonical record when possible.

---

# 36. TAGS

Monster News articles should support tags.

Tags should be database-driven.

The administrator should be able to:

- Create tags
- Rename tags
- Remove tags
- Apply tags
- Search by tags

Tags are not the same thing as hierarchy.

An article can have multiple tags without belonging to multiple categories.

---

# 37. RELATIONSHIPS

Monster News should support related-content relationships.

An article may relate to:

- Another article
- A category
- A dependency
- An API Group agency
- An API Group person
- An API Group jurisdiction
- A civic organization
- A source

Relationships should be structured.

---

# 38. SOURCES

News articles should support source information.

A source may include:

- Name
- URL
- Publication
- Date
- Description
- Document
- Notes

Source information should not be buried permanently inside article text.

# 53. CONTROL PANEL INDEPENDENCE

The Monster News control panel must remain distinct from the API Group control system.

Do not create a single undifferentiated editorial interface that makes the two systems appear to be one publication.

API GROUP

or:

MONSTER NEWS

---

# 54. ARTICLE TEMPLATES

Monster News should have its own article templates.

Templates may include:

- Standard news article
- Flash news article
- Investigation article
- Feature article
- Other future formats

The administrator should be able to add or modify templates without restructuring the API Group system.

---

# 55. TEMPLATE DATA

Templates should consume structured article data.

The article template should not become the database.

The article record should remain independent of the template.

This allows Monster News templates to change without destroying article data.

---

Its:

- Articles

- Dependencies

# 66. FINAL MONSTER NEWS PRINCIPLE

Monster News is a flexible, database-driven news publication.

Its hierarchy is:

MONSTER NEWS
→ CATEGORY
→ DEPENDENCY
→ ADDITIONAL DEPENDENCY LEVELS
→ ARTICLE

But this hierarchy is not hard-coded.

It is created and maintained through structured database records.

The administrator controls the hierarchy.

The database stores the hierarchy.

The website displays the hierarchy.

---

# 67. FINAL SEPARATION PRINCIPLE

API Group and Monster News are independent.

API Group is the structured information and relationship collection.

Monster News is the news publication.

Monster News may draw upon API Group information.

API Group information may be referenced by Monster News.

But neither system should be swallowed by the other.

- Expandable
- Editable
- Searchable
- Image-supported

---

# 69. GOLDEN RULE

Before implementing any Monster News feature, ask:

Can the content be exported?

Can the hierarchy be exported?

Can the relationships be exported?

Can the articles be moved?

Can the media be moved?

Can another application understand the data?

Can another CMS use the data?

Can another AI work with the data?

If the answer is unclear, stop and resolve the portability issue before implementation.

**MONSTER NEWS MUST REMAIN PORTABLE.**
