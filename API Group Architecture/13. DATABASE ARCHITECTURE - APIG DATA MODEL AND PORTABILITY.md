# DATABASE ARCHITECTURE — APIG DATA MODEL AND PORTABILITY

## PURPOSE

This document defines the database architecture requirements for API Group.

The API Group website is a database-driven information system.

The database is the source of truth for the underlying collection.

The website is the presentation and interaction layer.

The purpose of this document is to establish the requirements for selecting, designing, implementing, accessing, maintaining, and migrating the API Group database.

This document does not treat the database as merely a place to store webpage content.

The database is the structured foundation that allows API Group to connect people, agencies, jurisdictions, civic organizations, articles, sources, documents, and other information.

---

# 1. THE DATABASE-FIRST PRINCIPLE

API Group must be built around structured data.

The fundamental relationship is:

DATA
→ DATABASE
→ DATA ACCESS / API
→ APPLICATION
→ PRESENTATION
→ USER

The website must not become the primary source of truth.

A webpage is a view of information.

A profile page is a view of a record.

A directory is a view of records.

A sidebar is a view of records or navigation data.

A card is a view of a record.

The underlying information belongs in the structured data system.

---

The API Group collection contains relationships that cannot be adequately represented as isolated documents.

Examples include:

PERSON
→ works for
→ AGENCY

PERSON
→ located in
→ CITY

PERSON
→ connected to
→ CIVIC ORGANIZATION

AGENCY
→ operates in
→ COUNTY

AGENCY
→ belongs to
→ STATE

ARTICLE
→ references
→ PERSON

ARTICLE
→ references
→ AGENCY

ARTICLE
→ references
→ COUNTY

ARTICLE
→ references
→ CIVIC ORGANIZATION

SOURCE
→ supports
→ ARTICLE

SOURCE
→ supports
→ PROFILE

The database therefore needs a strong relational model.

---

# 3. DATABASE TECHNOLOGY

The preferred production database should be a mature relational database capable of supporting:

- Complex relationships
- Many-to-many relationships
- Full-text search
- Large collections
- Multiple users
- Concurrent access
- Structured queries
- Geographic information where needed
- Reliable backups
- Data export
- Data migration
- API access
- AI access
- Long-term scalability

A PostgreSQL-based architecture should be considered the leading candidate because it provides a strong relational foundation, extensive data types, powerful indexing, mature tooling, and good support for complex relationships and geographic data.

However, the specific database technology must remain an implementation decision subject to the Golden Rule.

The selected database must not become a reason that the API Group collection cannot be migrated.

The important requirement is:

**Use a powerful relational database while keeping the underlying data portable.**

---

# 4. PORTABILITY OVERRIDES DATABASE BRAND

The name of the database technology is less important than the portability of the information stored within it.

API Group must be able to export its collection into portable representations.

The architecture should avoid unnecessary use of proprietary features that would make migration difficult.

Where advanced database-specific functionality is used, that dependency should be documented.

---

# 5. STABLE IDENTIFIERS

Every significant entity should have a stable unique identifier.

Examples:

- Person ID
- Agency ID
- Jurisdiction ID
- Civic Organization ID
- Article ID
- Source ID
- Document ID
- Media ID
- Category ID

Identifiers should remain stable even when:

- Names change
- URLs change
- Page templates change
- Navigation changes
- The CMS changes
- The frontend changes

The URL is not the identity of a record.

The database identifier is.

---

# 6. CORE ENTITY TYPES

The API Group database should support, at minimum, the following conceptual entity types:

- People / Personnel
- Agencies
- Jurisdictions
- Civic Organizations
- Articles
- Sources
- Documents
- Media
- Categories
- Tags
- Relationships
- Administrative metadata

Additional entity types may be added as the project develops.

The database must be extensible.

---

# 7. PERSONNEL RECORDS

Personnel are independent canonical records.

A personnel record should contain information such as:

- Unique ID
- Name
- Preferred/display name
- Photograph
- Biography or description
- Position/title
- Contact information where appropriate
- Status
- Dates
- Sources
- Relationships
- Related articles
- Related agencies
- Related jurisdictions
- Related civic organizations

The exact fields may evolve.

The important architectural rule is that the person exists independently of any particular agency or jurisdiction.

---

# 8. PERSON-TO-AGENCY RELATIONSHIPS

A person may have relationships with multiple agencies.

Examples:

PERSON
→ employed by
→ AGENCY

PERSON
→ formerly employed by
→ AGENCY

PERSON
→ appointed to
→ AGENCY

PERSON
→ serves on
→ AGENCY

PERSON
→ leads
→ AGENCY

The relationship itself may need metadata.

For example:

- Relationship type
- Start date
- End date
- Title
- Source
- Status
- Notes

Do not store this information only inside the person's biography.

---

# 9. AGENCY RECORDS

Agencies are independent records.

An agency record may contain:

- Unique ID
- Name
- Description
- Logo/image
- Agency type
- Jurisdiction
- Address
- Website
- Contact information where appropriate
- Status
- Sources
- Personnel
- Related articles
- Related organizations
- Related jurisdictions

Agency types may include:

- Federal
- State
- County
- City
- Village
- Civic

The taxonomy must remain editable.

---

# 10. JURISDICTIONS

Jurisdictions should be represented as structured records.

Examples include:

- United States / Federal
- Illinois
- Counties
- Cities
- Villages

A jurisdiction may contain or relate to:

- Agencies
- Personnel
- Civic organizations
- Articles
- Documents
- Sources

Jurisdictions should not be implemented merely as folders.

They are entities in the database.

---

# 11. ILLINOIS FOCUS

API Group's primary geographic focus is Illinois.

Federal information may be included when it is relevant to Illinois.

The database should therefore be capable of representing relationships such as:

FEDERAL AGENCY
→ relevant to
→ ILLINOIS

FEDERAL PROGRAM
→ affects
→ ILLINOIS COUNTY

FEDERAL GRANT
→ associated with
→ ILLINOIS AGENCY

This allows federal information to be included without turning API Group into a general national database.

---

# 12. COUNTIES

Counties should be database records.

The county directory should not be manually hard-coded.

If the database contains:

County A
County B
County C

the system should automatically be capable of displaying those records in appropriate county directories.

When another county record is added, it should automatically become available to database-driven displays.

---

# 13. CITIES AND VILLAGES

Cities and villages should also be independent jurisdiction records.

A city or village may have relationships with:

- Counties
- Agencies
- Personnel
- Civic organizations
- Articles
- Documents
- Sources

A city or village should not be represented solely as a subpage.

---

# 14. CIVIC ORGANIZATIONS

Civic organizations are independent records.

A civic organization may include:

- Name
- Description
- Image/logo
- Type
- Location
- Website
- Personnel
- Agencies
- Jurisdictions
- Articles
- Sources
- Relationships

The civic category should remain flexible because civic relationships can cross county, city, village, and agency boundaries.

---

# 15. ARTICLES

Articles are independent content records.

An article should contain structured information such as:

- Unique ID
- Title
- Subtitle
- Summary
- Body
- Featured image
- Additional media
- Author
- Publication date
- Modification date
- Status
- Category
- Dependencies
- Tags
- Sources
- Related records
- Featured status

Articles may belong to API Group or Monster News depending on which independent system owns the article.

---

# 16. SOURCES

Sources are first-class information.

A source may include:

- Source ID
- Title
- Organization
- URL
- Publication date
- Retrieval date
- Document identifier
- Description
- Source type
- Notes

Sources may be connected to:

- Profiles
- Personnel
- Agencies
- Jurisdictions
- Articles
- Documents

The source relationship should be preserved.

---

# 17. DOCUMENTS

Documents should be independently represented where appropriate.

A document may include:

- Document ID
- Title
- File
- File type
- Description
- Source
- Publication date
- Retrieval date
- Agency
- Person
- Jurisdiction
- Article relationships
- Metadata

Documents should remain exportable independently of the CMS media library.

---

# 18. MEDIA

Images and other media should have independent records where appropriate.

Media may include:

- Media ID
- File
- Filename
- MIME type
- Caption
- Alt text
- Source
- Copyright information
- Description
- Upload date
- Related records

Images should not be trapped inside page-builder content.

---

# 19. CATEGORIES

Categories are structured data.

They should have:

- Category ID
- Name
- Description
- Image
- Parent category
- Status
- Sort order
- Metadata

Categories must be editable by administrators.

---

# 20. HIERARCHIES

The database must support hierarchical relationships.

Example:

API GROUP
→ Agency Profiles
→ State
→ Illinois
→ State Agency
→ Agency Record

Another example:

MONSTER NEWS
→ Investigations
→ Public Accountability
→ Government Spending
→ Article

The hierarchy should be represented through structured relationships.

It should not be hard-coded into page templates.

---

# 21. INFINITE OR PRACTICALLY UNLIMITED DEPTH

The system should not impose an artificial two-level or three-level limit on categories and dependencies.

A parent may have children.

A child may have children.

Those children may have additional children.

The system should support additional hierarchy levels as the project requires.

The administrator should not require a programmer to create a new level.

---

# 22. MANY-TO-MANY RELATIONSHIPS

The database must support many-to-many relationships.

For example:

One person may be connected to many agencies.

One agency may have many personnel.

One article may reference many people.

One person may be referenced by many articles.

One agency may serve multiple jurisdictions.

One jurisdiction may contain many agencies.

One civic organization may connect with many agencies and people.

These relationships must not be forced into a single-parent structure.

---

# 23. RELATIONSHIP RECORDS

Where a relationship has meaningful attributes, the relationship itself should be represented as structured data.

For example:

PERSON
↕
EMPLOYMENT RELATIONSHIP
↕
AGENCY

The relationship may include:

- Type
- Start
- End
- Position
- Source
- Notes
- Status

This allows API Group to represent real-world relationships accurately.

---

# 24. CROSS-JURISDICTIONAL RELATIONSHIPS

The system must support crossover.

A person may be connected to:

- A county
- A city
- A village
- A state agency
- A civic organization

at the same time.

A civic organization may operate across multiple jurisdictions.

An agency may serve multiple jurisdictions.

The database must not force everything into one geographic branch.

---

# 25. DATABASE-DRIVEN NAVIGATION

Navigation should query the database.

Examples:

County list
→ database query

Agency list
→ database query

Personnel list
→ database query

News category list
→ database query

Dependency list
→ database query

The number of records should never be assumed.

---

# 26. DATABASE-DRIVEN SIDEBARS

Sidebars should be capable of querying the database.

Examples:

COUNTIES
→ SELECT applicable county records

AGENCIES
→ SELECT applicable agency records

RELATED PERSONNEL
→ SELECT people connected to current record

RELATED ARTICLES
→ SELECT articles connected to current record

The sidebar is a presentation of data.

It is not the source of data.

---

# 27. SEARCH

The database must support search across appropriate fields.

Search should eventually be capable of finding:

- People
- Agencies
- Jurisdictions
- Civic organizations
- Articles
- Documents
- Sources
- Categories

Search should return the canonical records.

Search should not create duplicate records simply because the same entity appears in multiple contexts.

---

# 28. FILTERING

The system should support structured filtering.

Examples:

Personnel by agency.

Personnel by jurisdiction.

Agencies by type.

Agencies by county.

Articles by category.

Articles by date.

Articles by related agency.

Articles by related personnel.

Sources by type.

Filters should operate against structured data.

---

# 29. FULL-TEXT SEARCH

The selected database architecture should support efficient full-text search or integration with a dedicated search service.

The search implementation must preserve portability.

If a separate search engine is eventually used, the search index should be treated as a derived resource.

The database remains the source of truth.

---

# 30. AI ACCESS

AI must be able to work with structured API Group data.

AI should eventually be able to:

- Read records.
- Create records.
- Update records.
- Suggest relationships.
- Find missing information.
- Identify duplicate records.
- Extract information from sources.
- Generate summaries.
- Assist with article creation.

AI access should occur through controlled data-access mechanisms.

---

# 31. AI MUST NOT BYPASS THE DATA MODEL

AI should not create a profile by simply generating a webpage.

AI should create or update structured records.

For example:

INCORRECT:

AI
→ writes HTML page
→ page becomes the profile

CORRECT:

AI
→ structured record
→ database
→ profile template
→ public page

---

# 32. DUPLICATE PREVENTION

The database should eventually support duplicate detection.

If AI encounters:

"John Smith"

and a John Smith record already exists, it should not automatically create another record without determining whether the records represent the same person.

Potential duplicate detection may use:

- Name
- Organization
- Position
- Location
- Existing identifiers
- Sources
- Other distinguishing information

---

# 33. DATA VALIDATION

Records should have validation rules.

Required fields should be identified.

Invalid relationships should be prevented where practical.

Examples:

A relationship should not point to a nonexistent agency.

An article should not reference a nonexistent person.

A category should not reference a nonexistent parent.

Validation protects database integrity.

---

# 34. AUDITABILITY

Important database changes should be traceable where practical.

The system should consider recording:

- Who made the change
- When it was made
- What changed
- Previous value
- New value
- Source of the change
- Whether the change was AI-generated or human-generated

This becomes especially important as AI begins modifying records.

---

# 35. HUMAN AND AI CONTENT

Human-created and AI-assisted information should use the same underlying data structures.

The system may record provenance indicating:

- Human-entered
- AI-assisted
- Imported
- Automatically generated
- Sourced from an external dataset

But the resulting information should remain part of the same portable database.

---

# 36. IMPORTS

The database should support importing structured data.

Potential import formats include:

- CSV
- JSON
- XML
- Other documented formats

Imports should validate data before committing it.

---

# 37. EXPORTS

The database should support exporting structured data.

Exports should preserve:

- IDs
- Fields
- Relationships
- Categories
- Sources
- Metadata
- Dates
- Status

A simple webpage export is not sufficient.

---

# 38. RELATIONSHIP EXPORT

Export functionality must preserve relationships.

For example, exporting a personnel record should not merely export:

"Jane Doe"

It should preserve the relationships connecting Jane Doe to:

- Agencies
- Jurisdictions
- Civic organizations
- Articles
- Sources

where those relationships are part of the collection.

---

# 39. BACKUPS

Backups should preserve the underlying database.

The backup strategy should account for:

- Full database backups
- Incremental or point-in-time recovery where appropriate
- Media
- Documents
- Configuration
- Exportable data

Backups should be tested.

A backup that cannot be restored is not a reliable backup.

---

# 40. MIGRATION

The database architecture must anticipate future migration.

Possible future changes include:

- CMS replacement
- Database replacement
- Hosting replacement
- Frontend replacement
- Search replacement
- AI replacement

The data model should be documented well enough that another system can reconstruct the collection.

---

# 41. DATABASE SCHEMA DOCUMENTATION

The schema must eventually document:

- Entity names
- Field names
- Data types
- Required fields
- Optional fields
- Identifiers
- Relationships
- Relationship types
- Enumerations
- Taxonomies
- Validation rules

The schema documentation is itself part of the portable architecture.

---

# 42. API / DATA ACCESS LAYER

The website should not necessarily communicate directly with every database table.

A data-access or API layer should provide controlled access to the structured collection.

Conceptually:

DATABASE
↓
DATA ACCESS / API
↓
WEBSITE
↓
ADMINISTRATOR / PUBLIC USER / AI

This provides separation between the database and presentation layer.

---

# 43. APPLICATION INDEPENDENCE

The database must not depend upon a specific frontend.

A future application should be capable of using the same data.

For example:

CURRENT WEBSITE
→ API Group database

FUTURE MOBILE APP
→ same API Group database

FUTURE AI INTERFACE
→ same API Group database

FUTURE WEBSITE
→ same API Group database

---

# 44. CMS INDEPENDENCE

The database must not be designed solely around the internal content model of one CMS.

The CMS may manage the data.

It must not own the conceptual architecture.

The conceptual data model belongs to API Group.

---

# 45. PRESENTATION INDEPENDENCE

The same record should be capable of being presented in multiple ways.

For example, a personnel record might appear as:

- Search result
- Directory entry
- Sidebar item
- Card
- Full profile
- Related record
- Article reference

These are different presentations of the same underlying record.

---

# 46. NO DUPLICATION FOR PRESENTATION

Do not duplicate the underlying record merely because it appears in multiple places.

One canonical person should remain one canonical person.

One agency should remain one canonical agency.

One article should remain one canonical article.

The presentation may change.

The record does not.

---

# 47. CANONICAL RECORDS

Every major entity should have one canonical record.

References throughout the system should point to that record.

This prevents:

- Duplicate profiles
- Conflicting information
- Broken relationships
- Difficult migrations

---

# 48. SLUGS AND URLS

Slugs and URLs are presentation/navigation concerns.

They should not be treated as the permanent identity of a record.

If a URL changes, references should still be resolvable through the stable record identifier.

Redirect mechanisms may be used where appropriate.

---

# 49. DATABASE-GENERATED LISTS

Any list that represents a collection of records should be capable of being generated from the database.

Examples:

- All counties
- All agencies
- All personnel
- All cities
- All villages
- All civic organizations
- All articles
- All dependencies

Do not manually maintain these lists in templates.

---

# 50. ADDING A NEW RECORD TEST

The architecture must support this basic test:

1. Administrator creates a new record.
2. Record is saved to the database.
3. Record receives a stable identifier.
4. Appropriate relationships are established.
5. Record becomes available to search.
6. Appropriate directory displays recognize it.
7. Appropriate sidebars recognize it.
8. Appropriate cards recognize it.
9. Appropriate breadcrumbs recognize it.
10. No manual template modification is required.

---

# 51. REMOVING A RECORD

Deleting or archiving a record must be handled carefully.

The system should identify relationships before destructive deletion.

Where appropriate, records should be archived rather than permanently deleted.

References should not silently point to nonexistent records.

---

# 52. RECORD STATUS

Records should support appropriate status values.

Examples:

- Draft
- Published
- Archived
- Hidden
- Pending review

The exact status system may evolve.

---

# 53. VERSIONING

Important records should eventually support revision history where practical.

This is especially valuable for:

- Personnel
- Agencies
- Articles
- Sources
- Relationships

Information changes over time.

The system should not necessarily overwrite history without trace.

---

# 54. TEMPORAL INFORMATION

Many relationships change over time.

Examples:

A person works for Agency A in 2024.

The person moves to Agency B in 2026.

The database should be capable of representing both relationships and their applicable dates.

Historical information is part of the collection.

---

# 55. LOCATION DATA

Because API Group is geographically focused, the database should be capable of storing geographic information where useful.

Potential information includes:

- State
- County
- City
- Village
- Address
- Coordinates
- Geographic boundaries where necessary

Geographic functionality should be implemented in a portable manner wherever practical.

---

# 56. SECURITY

Database access must be controlled.

Public users should not have unrestricted database access.

Administrative operations should require appropriate authentication and authorization.

AI access should be controlled.

Sensitive administrative information should not automatically become public.

---

# 57. DATA OWNERSHIP

API Group owns the conceptual collection.

Third-party services may process the data.

That does not transfer ownership of the collection.

Vendor terms and technical architecture should be reviewed before storing critical information in external systems.

---

# 58. MONSTER NEWS DATABASE SEPARATION

Monster News is independent from API Group.

Monster News may have its own database or its own clearly separated data domain.

It should not become a hidden subsection of the API Group database model merely because the two systems can reference one another.

Cross-system references may be supported.

Cross-system ownership should not be confused with relationships.

---

# 59. API GROUP / MONSTER NEWS REFERENCES

A Monster News article may reference an API Group record.

For example:

MONSTER NEWS ARTICLE
→ references
→ API GROUP PERSONNEL RECORD

or:

MONSTER NEWS ARTICLE
→ references
→ API GROUP AGENCY RECORD

The reference should identify the canonical API Group record.

Monster News should not need to duplicate the entire API Group profile.

---

# 60. DERIVED DATA

Some information may be generated from the database.

Examples:

- Search indexes
- Cached pages
- Sidebar lists
- Navigation menus
- Card collections
- Statistics
- Feeds

These are derived representations.

The underlying database remains authoritative.

---

# 61. CACHING

Caching may be used to improve performance.

However, cached content must be considered temporary derived data.

A cache must never become the only surviving copy of important information.

---

# 62. PERFORMANCE

The database should be designed for growth.

The architecture should anticipate increasing numbers of:

- Personnel
- Agencies
- Jurisdictions
- Civic organizations
- Articles
- Sources
- Documents
- Relationships

Performance should be addressed through appropriate:

- Indexes
- Queries
- Pagination
- Caching
- Search architecture
- Database design

rather than hard-coded limits.

---

# 63. LARGE PERSONNEL COLLECTIONS

Personnel directories may eventually contain large numbers of records.

The interface should therefore support:

- Search
- Filtering
- Pagination
- Sorting
- Compact listings
- Thumbnails
- Names
- Positions
- Organizations
- Jurisdictions

A large personnel database should not be forced into a massive grid of cards.

---

# 64. DATA NORMALIZATION

The database should avoid unnecessary duplication.

For example:

Do not store the complete agency name separately in every personnel record when a relationship to the agency record can provide that information.

Do not duplicate a person's complete profile inside every article that references them.

Store the canonical record and reference it.

---

# 65. DENORMALIZATION

Controlled denormalization may be used when necessary for performance.

If it is used, the canonical source of truth must remain clear.

Performance optimizations must not create conflicting copies of important information.

---

# 66. EXTENSIBILITY

The data model must allow new record types and relationship types to be introduced later.

API Group is expected to grow.

Do not build the database around a fixed assumption that the current list of record types is permanent.

---

# 67. NO ARTIFICIAL RECORD LIMITS

The architecture must not assume a fixed number of:

- Counties
- Agencies
- Personnel
- Cities
- Villages
- Civic organizations
- Articles
- Categories
- Dependencies

The number of records is determined by the collection.

---

# 68. ADMINISTRATIVE DATA ENTRY

The administrator interface should make structured data entry understandable.

The administrator should not need to understand database tables.

Instead, the interface should present meaningful concepts:

PERSON
AGENCY
COUNTY
CITY
VILLAGE
CIVIC ORGANIZATION
ARTICLE
SOURCE
RELATIONSHIP

The system handles the underlying database mechanics.

---

# 69. AI DATA ENTRY

AI should use the same conceptual model.

When AI encounters a new person:

Create or identify a PERSON record.

When AI encounters a new agency:

Create or identify an AGENCY record.

When AI discovers a relationship:

Create or update the appropriate RELATIONSHIP.

When AI discovers a source:

Create or identify a SOURCE record.

This keeps the AI aligned with the architecture.

---

# 70. DATA PROVENANCE

Where practical, important information should retain provenance.

The system should be able to determine:

Where did this information come from?

When was it obtained?

Who or what entered it?

What source supports it?

Was it modified?

This is especially important for research-oriented records.

---

# 71. RELATIONSHIP PROVENANCE

Relationships should also be supportable by sources.

For example:

PERSON
→ works for
→ AGENCY

should be capable of having a supporting source.

This is preferable to placing an unsupported relationship into a profile narrative.

---

# 72. ARTICLE RELATIONSHIPS

Articles may connect to multiple entities.

For example:

ARTICLE
→ PERSON
→ AGENCY
→ COUNTY
→ CITY
→ CIVIC ORGANIZATION
→ SOURCE

The article should not have to duplicate all of those records.

It should reference them.

---

# 73. PROFILE RELATIONSHIPS

Profiles may also connect to articles.

PERSON
→ Related Articles

AGENCY
→ Related Articles

COUNTY
→ Related Articles

CIVIC ORGANIZATION
→ Related Articles

This allows information to be discovered from either direction.

---

# 74. BIDIRECTIONAL DISCOVERY

The system should support discovering relationships in both directions.

From a person:

Who is this person connected to?

From an agency:

Who works here?

From a county:

Which agencies and people are connected to this county?

From an article:

Which profiles does this article reference?

From a profile:

Which articles reference this profile?

This is a major benefit of the relational model.

---

# 75. DATA INTEGRITY

The database must maintain referential integrity wherever practical.

A relationship should not silently point to a nonexistent record.

A deleted record should not leave uncontrolled orphan references.

Changes should be validated.

---

# 76. PORTABLE SCHEMA

The conceptual schema should be documented independently of the selected database software.

A future developer should be able to understand:

PERSON
AGENCY
JURISDICTION
CIVIC ORGANIZATION
ARTICLE
SOURCE
RELATIONSHIP

without needing access to the original CMS.

---

# 77. PORTABLE EXPORT PACKAGE

The long-term system should be capable of producing a portable export package containing:

- Structured records
- Relationship definitions
- Sources
- Metadata
- Media references
- Schema documentation

The exact export mechanism may evolve.

The principle does not.

---

# 78. DATABASE TEST ENVIRONMENT

The production database should not be the only environment.

Development and testing should be possible using a separate environment.

Test data should be clearly distinguished from production information.

---

# 79. SAMPLE DATA

Initial sample records should be used to demonstrate:

- People
- Agencies
- Jurisdictions
- Civic organizations
- Articles
- Sources
- Relationships

Sample data should be clearly marked as demonstration content.

It should be replaceable without altering the underlying architecture.

---

# 80. DATABASE ARCHITECTURE AND THE WEBSITE

The website should consume database records.

It should not dictate what records exist.

For example:

The website displays ten counties because the database contains ten applicable county records.

The website displays eleven counties after an eleventh record is added.

The database determines the collection.

The website presents the collection.

---

# 81. DATABASE ARCHITECTURE AND THE ADMINISTRATOR

The administrator should think in terms of records and relationships rather than tables.

The interface should hide unnecessary database complexity while preserving the underlying structured model.

---

# 82. DATABASE ARCHITECTURE AND AI

AI should think in terms of entities and relationships rather than webpages.

The AI should be capable of reasoning:

"These two articles refer to the same agency."

"This person already exists."

"This agency belongs to this jurisdiction."

"This source supports this relationship."

"This new county should appear in the county directory."

That is the intended AI/database relationship.

---

# 83. DATABASE ARCHITECTURE AND PORTABILITY

The Golden Rule applies directly to the database.

Before implementing a database feature, ask:

Can this information be exported?

Can its relationships be exported?

Can another system understand it?
