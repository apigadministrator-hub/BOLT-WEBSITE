# APIG-27 — Records, Documentation, and Version Control Specification

## Status

Active

## Purpose

This specification defines how APIG creates, stores, identifies, updates, preserves, retrieves, and transfers records and documentation.

The fundamental principle is:

CREATE
→ IDENTIFY
→ CLASSIFY
→ STORE
→ VERSION
→ PRESERVE
→ RETRIEVE
→ AUDIT
→ TRANSFER.

---

# 1. Core Principle

APIG's institutional knowledge must be preserved in persistent, identifiable, and retrievable records rather than depending solely on an individual person, AI conversation, AI model, or service provider.

---

# 2. Record

A record is information preserved because it has operational, administrative, evidentiary, historical, legal, governance, or accountability value.

---

# 3. Documentation

Documentation explains how APIG operates, what APIG requires, what has occurred, or how a system or process is structured.

---

# 4. Institutional Knowledge

Institutional knowledge includes information necessary for APIG to understand and continue its operations over time.

---

# 5. Persistent Knowledge

Material institutional knowledge should be stored in persistent resources.

---

# 6. Conversation Knowledge

Information existing only inside an AI conversation should not be assumed to be permanently available.

---

# 7. AI Independence

APIG's records should remain usable if the current AI model or provider changes.

---

# 8. Provider Independence

APIG should not depend on one AI provider as the sole repository of institutional knowledge.

---

# 9. Record Identity

Each material record should have a recognizable identity.

---

# 10. File Identity

Where practical, files should have meaningful names that communicate their purpose.

---

# 11. Folder Structure

Folders should organize records according to APIG's established resource hierarchy.

---

# 12. Root Resource

The APIG root resource contains the Start Here document that directs an AI or authorized user to the appropriate resource areas.

---

# 13. Start Here

The Start Here document is the entry point for an AI that needs to understand the APIG resource structure.

---

# 14. Resource Discovery

An AI should use the Start Here document to identify where relevant information is located.

---

# 15. No Unnecessary Master Index

APIG does not require a separate master index of every record when the root resource and folder structure adequately identify the available resource categories.

---

# 16. Root Document Maintenance

The Start Here document should be updated when a material resource category or root-level folder is added, removed, renamed, or materially reorganized.

---

# 17. Existing Resource Categories

Existing folders should not require root-document changes merely because another document is added inside an already established category, unless the root instructions need to identify that document specifically.

---

# 18. Specifications

Specifications define APIG rules, structures, processes, or operating requirements.

---

# 19. Records

Records document actual events, actions, decisions, communications, evidence, or other historical information.

---

# 20. Guidance

Guidance may explain recommended approaches without necessarily establishing mandatory requirements.

---

# 21. Evidence

Evidence is information supporting a factual assertion, event, decision, finding, or conclusion.

---

# 22. Source

A source identifies where information originated.

---

# 23. Source Preservation

Material source information should be preserved where practical.

---

# 24. External Source

An external source is information originating outside APIG.

---

# 25. Internal Source

An internal source is information originating within APIG.

---

# 26. AI-Generated Information

AI-generated information should remain distinguishable from independently verified source information.

---

# 27. AI Analysis

AI analysis should not automatically be treated as a verified factual record.

---

# 28. AI Recommendation

An AI recommendation should remain distinguishable from an authorized APIG decision.

---

# 29. APIG Decision

A material APIG decision should identify the appropriate decision-making authority where practical.

---

# 30. Decision Record

Material decisions should be recorded when future operations, accountability, or continuity depend on them.

---

# 31. Decision Context

A material decision record should preserve enough context to understand why the decision was made.

---

# 32. Decision Authority

The record should identify the authority responsible for the decision where practical.

---

# 33. Decision Date

Material decisions should include the relevant date where practical.

---

# 34. Record Date

Records should identify when the recorded event or information occurred when known.

---

# 35. Creation Date

Where useful, records should distinguish the date a record was created from the date the underlying event occurred.

---

# 36. Modification Date

Material records should identify when they were materially modified where practical.

---

# 37. Record Owner

A material record should have an identifiable responsible owner or authority where appropriate.

---

# 38. Record Custodian

A custodian may be responsible for maintaining the record without being the authority responsible for its contents.

---

# 39. Record Authority

The authority responsible for a record may differ from the person or system storing it.

---

# 40. Record Classification

Records should be classified according to applicable access, privacy, security, evidentiary, and operational requirements.

---

# 41. Public Record

A record designated for public access may be made publicly available according to applicable requirements.

---

# 42. Restricted Record

A restricted record is not available to the general public.

---

# 43. Confidential Record

A confidential record requires heightened access control.

---

# 44. Sensitive Record

A sensitive record may require additional protection because of its contents or potential impact.

---

# 45. Classification Authority

Classification decisions should follow applicable APIG authority.

---

# 46. Classification Review

Records should be reviewed when circumstances materially change.

---

# 47. Record Integrity

Material records should be protected against unauthorized alteration.

---

# 48. Authenticity

Where material, APIG should preserve evidence sufficient to establish the authenticity of a record.

---

# 49. Original Record

An original record is the authoritative version established for a particular purpose.

---

# 50. Copy

A copy reproduces an existing record.

---

# 51. Working Copy

A working copy may be modified during preparation without immediately becoming the authoritative record.

---

# 52. Final Record

A final record represents the completed version intended for official use or preservation.

---

# 53. Draft

A draft is an incomplete or proposed version.

---

# 54. Draft Status

Draft material should not be mistaken for an approved or final requirement.

---

# 55. Approval

Where approval is required, the record should identify its approval status.

---

# 56. Active Document

An active document is currently applicable.

---

# 57. Superseded Document

A superseded document has been replaced by a newer applicable version.

---

# 58. Archived Document

An archived document is preserved for historical or evidentiary purposes but is not normally used to govern current operations.

---

# 59. Version

A version identifies a particular state of a document.

---

# 60. Version Number

Material documents should use a consistent versioning system.

---

# 61. Version Change

A material change should result in an identifiable new version.

---

# 62. Minor Change

Minor changes may include formatting, spelling, or other non-substantive corrections.

---

# 63. Major Change

Major changes alter the substance, authority, requirements, structure, or meaning of a document.

---

# 64. Change Log

Material documents should maintain a change history where practical.

---

# 65. Change Description

A change log should explain what materially changed.

---

# 66. Change Authority

Material changes should identify who or what authority authorized the change where practical.

---

# 67. Change Date

Material changes should identify the effective date where appropriate.

---

# 68. Effective Date

The effective date identifies when a version becomes applicable.

---

# 69. Future Version

A future version may exist without becoming effective until its designated effective date.

---

# 70. Version Conflict

If multiple versions exist, the AI should determine which version is currently applicable.

---

# 71. Historical Version

Historical versions should be preserved when their history has continuing value.

---

# 72. Historical Applicability

A historical version may govern analysis of events occurring while that version was active.

---

# 73. Version Preservation

Previous versions should not be silently destroyed when preservation is required.

---

# 74. Silent Overwrite

Material historical information should not be silently overwritten.

---

# 75. Immutable Records

Where appropriate, finalized records should be protected from ordinary modification.

---

# 76. Corrected Record

When a finalized record must be corrected, the correction should preserve the history of the change where practical.

---

# 77. Correction

A correction should identify what was changed when that information is material.

---

# 78. Deletion

Material records should not be deleted without appropriate authority.

---

# 79. Record Destruction

Destruction of records should follow applicable retention and authorization requirements.

---

# 80. Retention

Records should be retained for as long as required by their purpose, authority, legal requirements, operational value, or applicable APIG policy.

---

# 81. Retention Schedule

Where practical, APIG may establish retention periods for categories of records.

---

# 82. Retention Exception

A record subject to investigation, litigation, audit, or other preservation requirements should not be destroyed merely because its ordinary retention period has expired.

---

# 83. Preservation Hold

A preservation hold temporarily prevents destruction or alteration of records that must be preserved.

---

# 84. Evidence Preservation

Relevant evidence should be preserved when its loss could materially affect an investigation, decision, audit, or accountability process.

---

# 85. Chain of Custody

Sensitive evidence may require documentation showing who possessed, transferred, or modified it.

---

# 86. Record Transfer

When a record moves between custodians or systems, material transfer information should be preserved where practical.

---

# 87. Record Location

Material records should have an identifiable storage location.

---

# 88. Resource Path

Where practical, the record's folder and file path should remain identifiable.

---

# 89. External Resource

If a record depends on an external resource, its external location should be identified where practical.

---

# 90. Broken Reference

A broken reference should be identified rather than silently replaced with an invented resource.

---

# 91. Missing Record

An AI must not fabricate the contents of a missing record.

---

# 92. Missing Documentation

If required documentation cannot be located, the AI should report the absence and determine whether escalation is required.

---

# 93. Duplicate Records

Duplicate records should be identified when duplication could cause confusion.

---

# 94. Canonical Record

Where multiple copies exist, APIG should identify the authoritative or canonical record when necessary.

---

# 95. Synchronization

Copies that are intended to remain synchronized should be updated according to an established process.

---

# 96. Unsynchronized Copy

An unsynchronized copy should not automatically be treated as current.

---

# 97. File Format

File format should be selected according to the purpose of the information.

---

# 98. Machine-Readable Documentation

Machine-readable formats should be preferred when AI systems or automated processes must reliably interpret or modify the information.

---

# 99. Plain Text

Plain-text files may be used for simple instructions, logs, configuration information, and other text-based records.

---

# 100. Markdown

Markdown files may be used for structured documentation intended to remain human-readable and machine-readable.

---

# 101. PDF

PDF may be used when fixed visual presentation, formal distribution, or preservation of a rendered document is important.

---

# 102. Spreadsheet

Spreadsheet formats may be used for structured tabular information.

---

# 103. Database

Databases may be used when structured records require querying, relationships, permissions, or transactional control.

---

# 104. File Format Selection

The easiest format for an AI to read or modify is not necessarily the best format for every record.

---

# 105. Source Format

Where practical, editable source material should be preserved separately from rendered distribution formats.

---

# 106. Rendered Format

A rendered format may be generated from an authoritative source document.

---

# 107. Source of Truth

APIG should identify which file or system is the authoritative source when multiple representations exist.

---

# 108. Code Documentation

When code is copied into an external service, APIG should preserve documentation identifying the code and where it was used.

---

# 109. External Code Record

A code-related record may include:

- Destination
- Purpose
- Date
- Version
- Exact code
- Source
- Configuration
- Dependencies
- Notes.

---

# 110. Exact Code Preservation

When exact code is operationally important, the exact deployed or copied version should be preserved where practical.

---

# 111. Code Is Not the Only Record

Documentation concerning how code was deployed or used may be as important as the code itself.

---

# 112. External Service Documentation

For code or configuration placed into an external service, APIG should preserve enough information for another authorized operator or AI to understand what was done.

---

# 113. AI Handoff

A replacement AI should be able to determine from persistent records:

- What has been completed
- What remains
- Where resources are located
- Which external systems are involved
- Which versions are current
- Which decisions have already been made.

---

# 114. Conversation-to-Record Transfer

Material information from an AI conversation should be transferred into persistent documentation when future continuity requires it.

---

# 115. No Conversation Dependency

A critical operational procedure should not exist only in a conversation transcript.

---

# 116. AI Provider Change

Changing from one AI provider to another should not require reconstructing APIG's institutional knowledge from memory alone.

---

# 117. Transfer Package

A material project may maintain a transfer package containing the information necessary for another authorized AI or human operator to continue the work.

---

# 118. Transfer Package Contents

A transfer package may contain:

- Current status
- Current specifications
- Current files
- Open tasks
- Decisions
- External systems
- Known problems
- Next actions.

---

# 119. Task Status

Material ongoing work should have a recognizable status.

---

# 120. Open Task

An open task remains incomplete.

---

# 121. Completed Task

A completed task has satisfied its completion requirements.

---

# 122. Blocked Task

A blocked task cannot proceed without resolving an identified condition.

---

# 123. Abandoned Task

An abandoned task has been intentionally discontinued.

---

# 124. Resumption

An abandoned or paused project may be resumed if authorized.

---

# 125. Continuity

Records should support continuity across:

- People
- AI models
- AI providers
- Software
- External services
- Organizational changes.

---

# 126. Searchability

Material records should be reasonably searchable.

---

# 127. Naming Convention

File names should communicate purpose and, where useful:

- APIG identifier
- Subject
- Version
- Status.

---

# 128. Stable Names

Frequently referenced resources should use stable names where practical.

---

# 129. Renaming

Renaming a referenced resource should account for existing references.

---

# 130. Folder Changes

Moving a resource should account for systems or documents that reference its previous location.

---

# 131. Root Update

If a new root-level resource category is created, the Start Here document should identify it.

---

# 132. Internal Additions

Adding a document inside an existing category does not necessarily require changing Start Here.

---

# 133. Resource Hierarchy

The resource hierarchy should remain understandable without requiring the AI to memorize prior conversations.

---

# 134. Resource Instructions

A folder may contain an instruction document explaining how its resources should be interpreted.

---

# 135. Folder-Level Guidance

Folder-level guidance should identify:

- Purpose
- Applicable documents
- Naming conventions
- Authority
- Special handling requirements.

---

# 136. Document-Level Guidance

A document may identify its own purpose, status, authority, version, and relationship to other documents.

---

# 137. Cross-References

Documents may reference related APIG resources.

---

# 138. Cross-Reference Accuracy

Cross-references should be updated when referenced resources are materially renamed or relocated.

---

# 139. Circular References

Documentation should avoid unnecessary circular dependencies that prevent an AI from determining where to begin.

---

# 140. Entry Point

The Start Here document remains the primary entry point for the root resource hierarchy.

---

# 141. Resource Traversal

An AI should navigate downward through the hierarchy according to task relevance.

---

# 142. Targeted Retrieval

The AI should retrieve only the resources reasonably necessary for the task when complete retrieval would be inefficient.

---

# 143. Broad Retrieval

Broad retrieval may be appropriate when the task concerns APIG's overall structure.

---

# 144. Record Security

Documentation must remain subject to APIG security and access requirements.

---

# 145. Public Resource Security

Publicly accessible resources must not contain information that should remain restricted.

---

# 146. Restricted Resource Security

Restricted resources should use appropriate access controls.

---

# 147. AI Resource Access

An AI may access only resources it is authorized to access.

---

# 148. External AI Access

An external AI should receive only the information necessary for its authorized task.

---

# 149. Resource Export

Exporting APIG resources to another AI or system should preserve applicable security and authorization requirements.

---

# 150. Data Minimization

Only necessary information should be transferred to an external system.

---

# 151. Secret Exclusion

Credentials and secrets should not be included in ordinary transfer packages unless specifically required and appropriately protected.

---

# 152. Record Accuracy

Records should accurately represent what is known.

---

# 153. Uncertainty

Uncertainty should be documented when it materially affects interpretation.

---

# 154. Assumption

An assumption should be distinguishable from an established fact.

---

# 155. Estimate

An estimate should be identified as an estimate.

---

# 156. Allegation

An allegation should remain distinguishable from a verified finding.

---

# 157. Finding

A finding should identify its evidentiary or decision basis where appropriate.

---

# 158. Source Separation

Source evidence should remain distinguishable from AI interpretation.

---

# 159. Attribution

Material statements should identify their source where necessary to establish accountability or reliability.

---

# 160. Record Integrity Review

Material records may be reviewed for completeness, consistency, and integrity.

---

# 161. Audit Trail

Material modifications should leave an audit trail where practical.

---

# 162. Auditability

An authorized reviewer should be able to determine what happened and when for material records.

---

# 163. AI Auditability

Where practical, AI-generated or AI-modified material records should identify the responsible AI system.

---

# 164. Human Review

Material AI-generated records may require human review according to applicable APIG rules.

---

# 165. Approval Status

Records requiring approval should clearly distinguish:

- Draft
- Submitted
- Approved
- Rejected
- Superseded.

---

# 166. Rejected Record

A rejected proposal may be preserved as a historical record without becoming an active requirement.

---

# 167. Supersession

When a document is replaced, the previous document should be marked as superseded where appropriate.

---

# 168. Archival

Historical records should be archived in a manner that preserves their context.

---

# 169. Archive Retrieval

Archived records should remain retrievable when legitimate historical analysis requires them.

---

# 170. Record Disposal

Disposal should be authorized and documented where required.

---

# 171. Disposal Verification

Where practical, material record destruction should be verified.

---

# 172. Backup

Material records should be backed up according to their importance.

---

# 173. Backup Independence

Critical backups should not depend exclusively on the same system whose failure they are intended to protect against.

---

# 174. Recovery

APIG should be able to restore important records from appropriate backups where practical.

---

# 175. Recovery Verification

Restored records should be checked for integrity where practical.

---

# 176. Disaster Recovery

Record systems should account for catastrophic loss where appropriate.

---

# 177. Continuity of Records

A system failure should not automatically result in loss of APIG's institutional knowledge.

---

# 178. Record Migration

When changing storage systems, material records should be migrated with sufficient metadata to preserve meaning.

---

# 179. Migration Verification

Important migrated records should be checked for completeness and integrity.

---

# 180. Legacy Systems

Records stored in legacy systems should remain understandable and accessible when required.

---

# 181. Legacy Conversion

Legacy records may be converted to newer formats when necessary, provided their meaning and material characteristics are preserved.

---

# 182. Conversion Record

Material conversions should be documented.

---

# 183. Metadata

Material records may require metadata such as:

- Author
- Date
- Version
- Status
- Authority
- Classification
- Source
- Location.

---

# 184. Metadata Integrity

Material metadata should be protected from unauthorized alteration.

---

# 185. Record Relationships

Records may be related to:

- People
- Organizations
- Positions
- Jurisdictions
- Events
- Tasks
- Decisions
- Evidence
- Other records.

---

# 186. Relational Navigation

Where the APIG system supports it, users and AI should be able to navigate between related records.

---

# 187. Accountability Navigation

Records concerning an event may be linked to the people, positions, organizations, authorities, and jurisdictions relevant to that event.

---

# 188. Chain-of-Command Navigation

Where an accountability matter involves organizational authority, records should be capable of being connected to the applicable authority chain.

---

# 189. Downstream Accountability

Where APIG's governing rules establish downstream accountability, records should support navigation from an authority to relevant downstream entities or records.

---

# 190. No Automatic Liability

A link between an authority and a downstream record does not by itself establish personal misconduct, fault, or legal liability.

---

# 191. Oversight Record

A record may identify that an authority had oversight responsibility without concluding that the authority caused the underlying event.

---

# 192. Supervisory Record

A record may identify supervisory responsibility without attributing the subordinate's conduct to the supervisor.

---

# 193. Appointment Authority

Appointment authority may be represented as an organizational relationship where applicable.

---

# 194. Authority Navigation

Where appropriate, an authorized user should be able to navigate:

AUTHORITY
→ APPOINTED BODY
→ ORGANIZATION
→ EXECUTIVE
→ STAFF
→ EVENT / RECORD.

---

# 195. Accountability Distinction

The system should distinguish:

- Direct conduct
- Supervisory responsibility
- Oversight responsibility
- Appointment authority
- Jurisdiction
- Organizational relationship.

---

# 196. No Conflation

These relationships must not automatically be treated as equivalent.

---

# 197. Record Context

A record should be interpreted in the context of the applicable organizational and jurisdictional structure.

---

# 198. Historical Structure

If organizational authority changes over time, historical records should preserve the authority structure applicable at the relevant time where practical.

---

# 199. Structural Change

Organizational restructuring should not erase historical relationships.

---

# 200. Historical Navigation

Authorized users should be able to understand historical authority relationships when necessary.

# 201. Core Principles

1. Persistent records preserve institutional knowledge.
2. APIG should not depend on one AI conversation for critical knowledge.
3. APIG should not depend on one AI provider for institutional continuity.
4. Start Here is the root entry point.
5. The resource hierarchy organizes information by purpose.
6. A separate master index is not required when the hierarchy is sufficient.
7. Start Here should change when root-level resource categories change.
8. Internal additions do not automatically require root changes.
9. Specifications and records are distinct types of information.
10. Material decisions should be recorded.
11. Material sources should be preserved.
12. AI analysis should remain distinguishable from source evidence.
13. AI recommendations should remain distinguishable from authorized decisions.
14. Records should have identifiable status and ownership where appropriate.
15. Material documents should use version control.
16. Historical versions should be preserved when required.
17. Material changes should be auditable where practical.
18. Material records should not be silently overwritten.
19. Material records should not be destroyed without authority.
20. File format should match the purpose of the information.
21. Markdown and plain text are appropriate for many machine-readable instructions.
22. PDF is appropriate when fixed presentation or formal distribution is important.
23. The authoritative source should be identified when multiple representations exist.
24. Exact deployed code should be preserved when operationally important.
25. Code documentation should identify where and how code was used.
26. AI handoffs should rely on persistent resources.
27. Material project status should be recorded.
28. Missing records must not be fabricated.
29. Broken references should be identified.
30. Sensitive records must follow security requirements.
31. External AI systems should receive only necessary information.
32. Secrets should normally remain outside ordinary documentation.
33. Records should distinguish fact, allegation, finding, assumption, estimate, and analysis.
34. Material records should be auditable.
35. AI-generated records should be attributable where practical.
36. Historical authority structures should be preserved when relevant.
37. Accountability navigation should connect relevant authority relationships.
38. Organizational relationships must not automatically establish personal liability.
39. Oversight, supervision, appointment authority, and direct conduct must remain distinguishable.
40. APIG records must support continuity across people, systems, AI models, and AI providers.

# 202. Record Creation Sequence

EVENT / DECISION / INFORMATION
→ DETERMINE RECORD VALUE
→ IDENTIFY SOURCE
→ CLASSIFY
→ CREATE
→ ASSIGN IDENTITY
→ STORE
→ VERSION
→ PRESERVE
→ MAKE RETRIEVABLE.

---

# 203. Document Change Sequence

PROPOSE CHANGE
→ IDENTIFY AUTHORITY
→ MODIFY
→ REVIEW
→ ASSIGN VERSION
→ RECORD CHANGE
→ APPROVE WHEN REQUIRED
→ MARK ACTIVE
→ PRESERVE PRIOR VERSION.

---

# 204. AI Continuity Sequence

CURRENT AI
→ IDENTIFY MATERIAL KNOWLEDGE
→ RECORD STATUS
→ RECORD DECISIONS
→ PRESERVE RESOURCES
→ PRESERVE EXTERNAL-SYSTEM CONTEXT
→ PROTECT SECRETS
→ TRANSFER
→ NEW AI READS START HERE
→ RETRIEVES RELEVANT RESOURCES
→ CONTINUES WORK.

---

# 205. Accountability Record Sequence

EVENT
→ IDENTIFY PERSON
→ IDENTIFY POSITION
→ IDENTIFY ORGANIZATION
→ IDENTIFY SUPERVISORY RELATIONSHIP
→ IDENTIFY OVERSIGHT RELATIONSHIP
→ IDENTIFY APPOINTMENT AUTHORITY
→ IDENTIFY JURISDICTION
→ LINK RELEVANT RECORDS
→ PRESERVE DISTINCTIONS
→ DO NOT AUTOMATICALLY ATTRIBUTE LIABILITY.

---

# 206. Change Control

This document may be modified as APIG develops.

Substantive changes should:

- Update the version.
- Record the change.
- Preserve previous versions where practical.
- Update the root resource document if the resource location changes.
- Identify specifications that require corresponding changes.
